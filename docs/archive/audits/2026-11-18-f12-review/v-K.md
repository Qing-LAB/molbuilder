# Verdicts — r1-K (MolView, judged on `docs/web/molview.md` only)

D1 | CONFIRMED | W | road: Molbuilder tab: select atoms → Delete (or any op that changes the count) → another edit → Retract; or Delete → reload the tab | In `model.js` `applyOp`'s `apply`, `recordEdit(checkpoint)` comes before `if (countChanged) selection.clear()`. `history.save(1)` → `request` → `send` runs synchronously in SETTLED, so `recordState()` reads `selection.get()` (the old indices). `persist` and `persistDraft` both get those bytes before the clear runs. The in-memory clear writes nothing afterwards: no selection change writes the draft. `restoreState` → `selection.adopt(state.selection)` does not filter, so a Retract onto that point, or `load(0)` on reload (`modify/viewer.js:806`), marks atoms that were never picked. This breaks § 11.2's "the atoms you had picked out". When the indices are past the end, `sourceIndexFor` drops them, the count reads "2 of 8 selected", and with isolate on the window is empty (`loadFrames([],…)`).
D2 | CONFIRMED | W (low) | road: a pair carrying `info.calculation` opened in the Molbuilder tab → Assign a label → reload before any other edit, or → another edit → Retract → Save | In `writeLabel`, `recordEdit(true)` runs before `markContractOutdated("labels")`. `recordState` deep-copies the structure synchronously inside `send`, so the point and the draft both lack `labels_modified`, while the live structure has it. A reload adopts the draft without the flag. The more common path is label → translate → Retract: the label point has no flag, and Save then writes a sidecar without it. This breaks § 8.4a ("the flag is recorded … both ride the pair"). Impact is small today: no Python reader of `labels_modified` exists (only `structure.py` writes it).
D3 | PLAUSIBLE | N (race; the effect is W if it is met) | road: Results tab on a live run: toggle isolate, or change the selection with isolate on, within a few ms of a poll answer | The mechanism is real. The replay then calls `embed.appendFrames` for `from..total-1` again (`doAppend` never compares against `drawnFrameCount`). `healIfShort` only catches a short drawing, and core.js's post-check reads the master `frameCount()`, not the drawing. Missing: a trigger inside the window. The window is one `setTimeout(0)` (`PAINT_YIELD`). Polls are one at a time (`pollInFlight`) every 15 s (`POLL_MS`), and a poll's own re-install adds no frames afterwards. The reviewer's background-tab case does not hold: no person toggles isolate in a hidden tab, and the next poll answer comes ≥15 s after the rebuild's ≤1 s throttled timer. Only a click within ~ms of a poll answer remains.

D6 | CONFIRMED | M (low) | road: Results tab, Show forces + Show axes (1.5 Å world triad) or Show unit cell (lattice-length a/b/c) | `applyOverlaysFor` concatenates the triads into `setArrows`. `redrawArrows` ranks every arrow in `state.arrows` (`maxAt` over all), and triad arrows carry `color` but no `radius`. ## CONFIRMED W / C

**D1 (W).** Someone in the Molbuilder tab deletes (or adds) atoms with a selection. The saved point and the draft keep the old selection indices, now pointing at different atoms or past the end. A Retract back to that point, or a reload of the tab, shows those atoms selected although the person never picked them. The next Delete, Assign or translate-by-selection then acts on them. With indices past the end and isolate on, the window goes blank while the count says "2 of N selected". Who: anyone who edits, then retracts or reloads. Smallest fix: in `applyOp`'s `apply`, clear the selection before `recordEdit(checkpoint)` (or inside the settle's change). The point and the draft then record the selection the person actually has.

**D2 (W, low).** Someone labels atoms in a pair that carries a recorded calculation. The point and the draft are written before the `labels_modified` flag is set. A reload right after the label, or a Retract onto the label's point, gives a structure whose recorded contract does not say the region assignment changed, and Save writes that sidecar. No reader uses the flag today, so the harm is a record that says less than § 8.4a promises. Smallest fix: call `markContractOutdated("labels")` before `recordEdit(true)` in `writeLabel` (inside the settle), so the flag is part of the recorded state.

**D8 (W).** Someone in the Molbuilder tab starts a server edit (slab, append, delete…) and, while it is on the wire, presses Assign (or Apply on the Cell form). The label lands and lays a point. The op's answer, built from the structure before the label, then replaces everything, and the label is gone with no message. The history shows "label, then not". A cell commit made in the same window is lost, or lands on the wrong atoms. Who: anyone who clicks during an op's round trip. Nothing disables those controls. Smallest fix: make one-in-flight model-wide. Lift `running` to the model and have `writeLabel`, `commitPeriodicityOp` and the `info`/`customized` writers answer `null` while it is set, as § 6.9 already lists. Or lock MolView's verb buttons and the Cell Apply while a structure door is in flight.

**D10 (W, low).** Someone edits several metadata entries at once through "Edit as JSON". Each changed key lays its own point, so one Retract restores only the last key and leaves a mixed store that was never on screen. A Save then writes that mix to the sidecar. Who: anyone using the raw-JSON editor on a multi-entry change. Smallest fix: wrap the Apply loop in `model.beginChange()` / `model.endChange()`. The history machine already holds the repeated `save(1)` requests and sends one point at the end with the settled store. A single "replace the store" door that records once would also do.
