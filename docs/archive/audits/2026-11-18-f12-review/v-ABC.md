## Confirmed W and C findings

**A-D1 (C): a write that fails during prep or launch ends in a traceback.** After the save before a prep (`_prep_groups`, `prep_bench`, `_record_the_order`) or before a group's first launch (`send_launch`), a write that fails raises `planned.CutShort`. That can be a full disk, a quota, or a file the person may not write. Nothing between it and the terminal catches it, so the person on a cluster whose quota fills mid-prep sees a Python stack. They do not see one line saying which write failed and which saved state takes them back. For prep, that state is named only in the ledger's `saved` line; launch prints `plan.saved` in its `finally`. The stage is correctly left not prepared, because its row is written last. **Smallest fix:** catch `CutShort` at the prep and launch entries the way `migrate` does. Write a ledger line saying how far the plan got, then raise `PrepError` or `SubmitError` naming the write that failed and the state to restore.

**B-D2 (W): the run script's USER-CUSTOM zone runs after the engine.** The zone is rendered as the script's tail, after `echo "… completed"` and `conclude_line(0)`. The failure arm has already run `exit "$_engine_exit"`. So whatever a person writes in the zone of the `.run.sh` (a `ulimit -s unlimited`, an `export OMP_STACKSIZE=…`, a `module load`) never reaches the engine and nothing says so. Every prep carries the zone forward, so the person keeps believing it applies. A line there that fails under `set -e` makes the job exit non-zero after `.concluded` reads `rc=0`. The exit trap leaves an existing marker alone, so the scheduler records FAILED while molbuilder reads finished. **Smallest fix:** emit the run script's zone before the engine starts, after the environment and activation, so what is put there acts on the run. If after-run steps are what the zone is for, job-contracts § 3.5 should say so, and the zone should run before the conclusion marker so that step 21 stays the main line's last act.

**B-D3 (W): the machine record says a never-asked submit cap was asked.** On a Slurm whose `sacctmgr` rejects `MaxSubmitJobsPerUser`, the probe falls back to the four-column QoS query. `parse_qos` stores `None` for the missing fifth column, which is the same value as a blank (uncapped) cell, and `derive_domains` copies it onto every domain. `Domain.to_row` then writes `"max_submit_jobs": null`. Under scheduler.md § 2, `null` means *asked, and the scheduler states none*, so the file the person keeps states the opposite of what happened. `no_submit_cap` reaches only a note printed once. Today's one reader (R14) treats `null` and absent alike, so no prep decision changes yet; the record is wrong. **Smallest fix:** when the fallback was used, or a row has no fifth cell, leave `max_submit_jobs` UNSET so it stays off the disk. For example, `parse_qos` can return UNSET for a missing column, or `derive_domains` can skip the copy when `no_submit_cap` is set.

**C-D1 (W): the person's git ignore settings decide what a save keeps, and a restore deletes the rest.** `_run_git` runs git with the person's whole configuration. Small files matched by the person's global excludes file (`core.excludesFile`, by default `~/.config/git/ignore`) or by `.git/info/exclude` are skipped by `git add -A`. They are not big, so the archive does not take them either, and `git status --porcelain -uall` never lists them as unsaved. A restore's sweep then unlinks every file that is neither tracked nor in the MANIFEST, so these go with no A5 warning. The person's own lines outside the generated block of the calculation's `.gitignore` have the same effect, which puts S1a's *left alone* at odds with S1's *never neither*. The git half was reproduced in scratch: with `*.log` and `*.out` in a global excludes file, `git add -A` stored only `x.fdf` and the status listed nothing. A person with those common entries keeps no `.out` under the size limit, no session, monitor or SCF-timing log and no `jobset-decisions.log` in any state. The sidebar reads *saved*, and any restore deletes all of them from every run folder. **Smallest fix:** run every checkpoint git call with the person's excludes neutralised, for example `-c core.excludesFile=/dev/null`, with `info/exclude` ignored likewise. As a backstop, have `status` count any walked regular file that is neither tracked, nor archived, nor `never_carried` as unsaved, so A5 names it before a restore removes it.
