D1 | CONFIRMED | M | road: SIESTA Raman at a laser with "Modes in a frequency range", a side pending or failed, or a PySCF Raman sweep followed mid-run | `_seal.js` `tracesFor` leaves every "pending" mode out of lane 0's bar trace, but `index.js` `recolour` → `surface.recolour` restyles that trace with `modes.map(stateOf)`, one entry per mode, by position. With p pending modes before the chosen one, the colours shift: real bands get the pending grey, the chosen colour lands past the end or on a neighbour, and the hover colour lands on the wrong stick. `_ramanOf` returns null for every mode the Raman view does not list (`(r && r.raman) ? null : …`), and `raman_view` lists only the picked modes. The note at `index.js:254` names this exact hazard for the floor but not for pending modes.
D2 | CONFIRMED | W (+C) | road: any export from the Results tab's mode box (PNG-zip is the default; WebM too) | `index.js` `exportAnimation` stamps `meta` (index, norm, amplitude, framesPerCycle) when the export starts, but `coordsAt` reads the live `structure`/`disp`/`amplitude`/`r.framesPerCycle`, and `compose` reads the live caption element. In `core.js`, `state.exporting` is checked only by `onExportAnimation` itself. A row click (`selectMode` → `_showMode` → `setAmplitude` + `showMode` + `play`) and the Size and Speed sliders all stay live, and `toBlob` and `setTimeout` give way to those clicks between frames. Any poll with a new fingerprint, and a return to the browser tab (D3), runs `renderResults` → `state.vib.dispose()` (`structure = null`). The next `coordsAt` then throws, and the status line shows "Cannot read properties of null (reading 'positions')" in red. (GIF is spared: its walk only `await`s values that are not promises, so no click gets in.)
D3 | CONFIRMED | N | road: any spectrum on the Results tab, then another browser tab and back | `_onVisibilityChange` → `loadByPath` → `transition("LOADING")` clears `fileState.results` and `viewState.selectedMode`. `renderResults` then sees `prev === null`, picks the default mode, disposes and rebuilds the viewer (camera re-fitted) and redraws the level diagram at full range. `results.md` § 4.2 resets `viewState` "on a file switch" only, and a return to the tab is not one. The loss is the person's place in the view. Losing a running export this way is counted under D2.
D4 | CONFIRMED | N | road: a run followed live (PySCF with the orbital probe on, or SIESTA optical calls landing with a laser applied) | `renderResults` stops only an identical fingerprint. That breaks `spectra.md` § 4 ("kept while you move between that result's modes, built afresh … when another result loads") and `vibrationview.md` § 5.1. Comfort only: a lost camera or zoom.

The workspace read is usually the faster of the two, which is why I could not show it happens.

## CONFIRMED W / C

**D2 (W, with a C path).** What goes wrong: someone exporting a mode animation (Results tab → spectrum → Mode visualisation → Save animation) gets a file that is not what the file says it is if they click another mode, or drag Size or Speed, while a PNG-zip or WebM export runs. The frames switch to mode B partway through and the burned-in caption changes with them, yet the file is named `vibration-mode-A` and its manifest states A's normalization and amplitude. After a Speed drag, a "one cycle" file no longer closes on itself. If the run is still being followed and a poll lands with new data, or the person switches browser tabs and comes back during the export, `renderResults` disposes the viewer. The export then dies with a raw "Cannot read properties of null (reading 'positions')" in red, and nothing is saved. Who: anyone exporting while clicking around, and anyone exporting from a live run or waiting on a WebM in another browser tab. Smallest fix: build the export's context from a snapshot taken when it starts. That means copying `structure.positions`, `disp`, `amplitude` and `framesPerCycle` into the `coordsAt` closure and fixing the caption text for the export's whole length. Then the frames match the metadata whatever the page does, and a later `dispose` cannot null them. Also have `dispose` abort a running export (the cancel path already says it in words). The tab may also hold mode selection and slider writes while `state.exporting` is set, but the snapshot alone makes the file true.
