## CONFIRMED W and C findings

**I-D1 (W).** A person who made a symlink inside the projects tree deletes, renames, moves or copies it from the sidebar. The server acts on the link's target instead. A recursive delete of a link to another calculation's folder wipes that calculation and leaves the link dangling, and a rename renames the target in its own parent folder. Smallest fix: the file routes act on the entry the person picked, not the resolved one. Delete unlinks a link and never runs rmtree on its target. Rename, move and copy refuse a symlink source, as `_writable` already refuses writing through one. The listing marks a link as `symlink` (test `is_symlink()` before `is_dir()`).

**I-D2 (W).** A person sends a hand-over into a folder, changes the run name, and sends again into the same folder. The page says the old hand-over was replaced, but the old label's template and source pair stay. Task setup then shows a template error and refuses Save ("holds 2 templates … remove the other") until the person deletes a file by hand. Smallest fix: when `task.1st.json` is already in the folder, the hand-over door reads its label. If the label differs, it removes that hand-over's template and source pair in the same publish, or refuses the send and names the old label.

**I-D3 (C).** When the projects disk is full or cannot be written, every workspace save answers Flask's HTML 500. The page can only say "the server's answer could not be read (HTTP 500)", so the person never learns why. Smallest fix: catch `OSError` around the `mkdir` and `write_json` in `ws_write_state` and answer `err(f"could not save the state: {exc}", 500)`. The broader fix is one `errorhandler(OSError)` in `app.py`, which would also make the `web-api.md` § 1 sentence (I-U2) true.

**J2-D1 (W).** A person opens a calculation's root, or one of its runs, then opens another run of the same calculation from the ladder. The Export bar keeps the first path, so Export downloads a different run's spectrum from the one on screen. For a displacement sweep, the export stays refused even with a stage's run open. Smallest fix: let the kept bar read its path when a button is pressed. `exportBar` can take `path` as a getter, as `asks` already is, and the viewer can pass the current selection's path.

**J2-D2 (C).** A person opens a SIESTA output in Results, and MolView fails to mount (no WebGL, a remote or VM browser, or a panel narrower than the card's floor). The load then throws a TypeError at `core.js:1911`, and the error text replaces "Viewer failed". No energy plot, force plot, badge or SCF line is drawn, though none of them needs the 3-D viewer. Smallest fix: guard on the data door as every other use does: `const countInSync = !_mvdata() || _mvdata().frameCount() === oldLen;`, and make `canAppend` depend on `_mvdata()`, not on `_mv`.
